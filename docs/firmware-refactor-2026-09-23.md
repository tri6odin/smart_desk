# Рефакторинг и проверка прошивки — 2026-09-23

Ветка: `codex/firmware-stability-refactor`, исходный commit `9c41bcc` из
`refactor/controller-fsm`. Работа выполняется поверх существующего FSM, без
смены GPIO, UART-протокола, BLE identity, NVS namespace или режимов сборки.

## Структура для сопровождения

| Модуль | Ответственность |
|---|---|
| `components/desk_protocol` | Кодирование и потоковый разбор UART |
| `components/desk_controller/desk_controller.cpp` | Переходы FSM, пределы, торможение, watchdog |
| `components/desk_controller/desk_inputs.cpp` | Проверка телеметрии и единый слот BLE-входов, без ESP-IDF |
| `components/desk_controller/desk_recovery.cpp` | Блокировка неизвестных ответов и автомат RST-калибровки |
| `main/production_main.cpp` | Production-задачи RX/TX, снимок входов, heartbeat, привязка к BLE |
| `main/preset_store.cpp` | Загрузка/сохранение SIT/STAND в прежних ключах NVS |
| `main/uart_transport.cpp` | Общая конфигурация UART для всех режимов |
| `main/ble_hid_logger.cpp` | BLE-соединение и семантика HID |
| `main/app_main.cpp` | Только исторические лабораторные режимы |

CMake включает одну точку входа. Production больше не зависит от условных
веток лабораторных экспериментов. Каждое состояние FSM имеет свой обработчик;
расчёт торможения и отслеживание прогресса определены в одном месте.
Проверку допустимости пресетов совместно используют FSM и NVS-адаптер.

Изменение логики движения нужно начинать с host-сценария в
`test_desk_controller.cpp`; правил приёма входов — с `test_desk_inputs.cpp`.
Внутри pure-компонентов не должно быть FreeRTOS, логирования, UART или NVS.
Общий lock в ESP-адаптере защищает снимки входов; блокирующие операции
выполняются после выхода из critical section. Время FSM — миллисекунды
`esp_timer_get_time()` по модулю 2^32; FreeRTOS ticks используются для сна задач.

## Исправленные дефекты и уточнения поведения

1. Одновременные dial reports и запрос пресета оставляли dial непотреблённым.
   Отклонённый пресет мог превратиться в движение на следующем цикле, а принятый
   — отмениться старым жестом. Теперь весь снимок потребляется один раз.
2. Старые dial reports могли запустить новый STEP/HOLD после задержки writer.
   Новый жест принимается только в пределах lease 350 мс. Уже принятый одиночный
   жест сохраняет штатное окно классификации 300 мс с учётом дискретизации
   writer; зависший классификатор прекращается через 650 мс от его старта.
3. Пресет на расстоянии 1–2,5 см мог выдать один HOLD до первой проверки
   торможения. Теперь движение не начинается внутри зоны выбега: до 2,5 см
   при подходе вверх и до 2,0 см при подходе вниз. Это намеренное изменение
   поведения; точное доведение из этой зоны не реализовано.
4. Перед выдачей STEP после классификации повторно проверяется возможность
   полного шага внутри пределов. Зона допуска HOLD также пересчитывается.
5. После паузы UART счётчик одинаковых кадров сохранял старую стабильность.
   Разрыв более 300 мс теперь начинает подтверждение заново с одного кадра.
   Аномальный кадр немедленно делает высоту непригодной; флаги, статус и диапазон
   проверяются в одном модуле по production-конфигурации 70–120 см.
6. STOP, кнопки и dial читаются одним согласованным снимком. STOP отменяет
   pending button независимо от порядка прихода до следующего чтения.
   После операции сохранения NVS старый снимок не используется для старта.
7. BLE bond list и его длина публикуются под одним lock вместо несогласованного
   чтения массива при обновлении из другого callback. В semantic timer время
   считывается под тем же lock, что и timestamp события, чтобы избежать ложного
   unsigned underflow при конкурентном обновлении.
8. Ошибки создания production/BLE-задач проверяются явно. Создание задачи не
   находится внутри `configASSERT`, который может быть отключён настройкой.
   Перед инициализацией BLE передаётся IDLE. Heartbeat TX обновляется после
   подтверждения завершения UART-передачи; при ошибке сбрасывается активное
   намерение, supervisor сохраняет контроль зависшего writer.

Первые четыре дефекта воспроизведены новыми host-тестами на исходной логике:
10 проваленных CHECK, исправленная логика проходит те же сценарии.
Порог третьего report, lease 350 мс, цели 80/115 см, пределы 70–120 см,
rearm 500 мс / 3 или 5 кадров и таймауты движения сохранены.

## Проверки

- Исходный baseline: 2/2 host-набора проходят.
- После изменений: 3/3 host-набора проходят (protocol, controller, inputs).
- Контроллер: 28 именованных сценариев, включая матрицы направлений/состояний,
  абсолютные watchdog, переполнение времени и 200 000 сгенерированных шагов.
- Входы: 7 сценариев с вариантами статусов, высот, порядка событий и времени.
- Production ESP-IDF 6.1: сборка успешна; бинарник `0xbb7f0` байт,
  свободно 50% app-раздела.
- Все семь диагностических режимов ESP-IDF 6.1 также собраны: read-only,
  idle, step-down, hold-down, ble-logger, ble-one-shot, ble-calibration.
  Вместе с production — 8/8 режимов; ошибок/предупреждений компилятора
  в исходниках проекта не обнаружено. Есть сообщения Kconfig и CMake
  из самого ESP-IDF о defaults/зависимостях компонентов.
- UBSan: 3/3 host-набора проходят с остановкой на первой ошибке.
- ASan+UBSan: все три теста превысили 30-секундный timeout, в том числе вне
  песочницы. Пустая программа `int main() { return 0; }`, собранная с теми же
  санитайзерами, тоже зависает. Это ограничение локального ASan runtime;
  проверка ASan не засчитана и должна быть повторена на другом host.

Команды host-проверок и production-сборки приведены в `firmware/README.md`.
Воспроизводимый запуск: `python3 tools/check_firmware.py`; дополнительно
`--all-modes` для матрицы ESP-IDF или `--sanitizers undefined` для UBSan.

## Что остаётся проверить на устройстве

Эта ветка не прошивалась. Host-тесты не подтверждают реальные тайминги BLE,
качество питания, поведение силовой платы после потери UART или механический
выбег. Причина первоначального редкого самопроизвольного HOLD не установлена
задним числом; нельзя считать её устранённой только по результатам рефакторинга.

Перед принятием версии:

1. Проверить одиночные и двойные reports, третий report и быстрый реверс;
   сравнить ощущения крутилки с текущей прошивкой.
2. Проверить SIT/STAND, в том числе запрос внутри зоны торможения, сохранение
   пресетов и сохранность BLE bond после обычной перепрошивки.
3. Проверить STOP, disconnect и пропажу/восстановление телеметрии из STEP/HOLD
   и движения к пресету. IDLE прекращает повторение HOLD; прекращение уже
   принятого автономного STEP определяется штатной платой и требует измерения.
4. Записать непрерывный serial log и выполнить серию жестов и reconnect;
   отслеживать причины переходов, неожиданный reboot и потерю реакции.
5. Проверить длительную работу и питание по существующему `next-steps.md`.

Критерии аппаратного допуска: нет самопроизвольного продолжения/повторного
старта, не выходят за границы, реакции STOP/disconnect соответствуют измерениям,
нет зависания задач и утраты BLE bond. После прогона сохранить результаты в
`measurements.md`. До этого версия является кандидатом, проверенным на host,
а не подтверждённым стабильным аппаратным релизом.
