# Внесение изменений

Рабочая ветка проекта — `main`.
Создайте отдельную ветку для изменения и откройте pull request.
История старой основной ветки сохранена в `codex/main-before-journal`.

## Подготовка

1. Прочитайте [обзор](README.md) и [архитектуру](docs/architecture.md).
2. Установите ESP-IDF 6.1 по [инструкции](firmware/README.md).
3. Создайте ветку: `git switch -c codex/описание-изменения`.
4. Определите требование и наблюдаемый результат до изменения кода.

## Изменение управления

Проследите весь путь ввода до UART.
Проверьте отмену движения, выбег, ошибочную телеметрию и восстановление после RST.
Не ставьте новые движения в очередь во время остановки.
Не считайте IDLE подтверждением физической остановки.
Не добавляйте аппаратные команды для проверки на работающем столе без отдельного сценария.

Для нового UART-кадра приложите исходный захват и описание опыта.
Разделяйте наблюдение, предположение и подтверждённую семантику.
Сначала проверьте полное совпадение байтов.
Обновите [протокол](docs/protocol.md) и [измерения](docs/measurements.md).

## Изменение журнала

Не меняйте смысл опубликованных числовых кодов.
Согласуйте C++-формат и Python-декодер.
Проверьте чтение прежнего дампа и сохранность разделов NVS/PHY/factory.
Новую подпись добавьте в [справочник](docs/log-reference.md).
Опишите, записывает ли событие реальную передачу, попытку передачи или изменение настроек.

## Проверка

1. Проверьте изменённую цепочку по коду.
2. Выполните подходящие host-проверки из [инструкции](firmware/README.md).
3. Соберите production. При изменении общего кода проверьте затронутые лабораторные режимы.
4. Для поведения оборудования составьте аппаратный опыт по [плану](docs/verification-plan.md).
5. Укажите выполненные проверки и оставшиеся ограничения в pull request.

Не заменяйте аппаратный результат успешным тестом модели.
Для исправления ошибки добавляйте проверку наблюдаемого отказа, а не копию реализации.

## Документация

Пишите по-русски: короткие предложения, постоянные термины, один шаг — одно действие.
Это адаптация принципов ASD-STE100, а не заявление о соответствии английскому стандарту.
Сохраняйте идентификаторы кода на английском.
Используйте нумерованные шаги для процедуры и таблицы для справочника.
Для схем используйте Mermaid, который отображается в GitHub.

[Карта документации](docs/README.md) определяет назначение каждого файла.
Не копируйте таблицы событий и временных порогов в несколько документов.
Не меняйте исторические результаты при обновлении текущего поведения.
Новые измерения привязывайте к commit, ELF и условиям питания.

## Отчёт об ошибке

Укажите модель ESP, commit, питание, пресеты, последовательность действий и фактический результат.
Приложите полный дамп, если готовы опубликовать историю движений и высот.
Сохраните исходный дамп до перепрошивки.
Для уязвимости используйте [порядок сообщения](SECURITY.md).
